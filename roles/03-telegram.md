# 03. Telegram и согласования

[К командному плану](../TEAM_PLAN.md) · [Общий контракт](../ARCHITECTURE.md) · [Доступы](../YANDEX_AND_AVATAR.md)

**Первая ветка** `feat/telegram-approval`. Владение `app/telegram/`, `tests/telegram/`. Первый PR показывает карточку, обработку решения и отказ чужому пользователю с тестовым транспортом.

## PR 1. Приём событий и карточки

1. Оберни Telegram Bot API в httpx. Настрой polling `getUpdates` с `allowed_updates` для сообщений и callback. У HTTP-вызова таймаут длиннее timeout polling. После надёжной записи update в SQLite можно продвинуть offset. Обработку сохранённого события возобновляет основной процесс. Падение парсера сохраняет безопасный статус и не блокирует поток.
2. Показывай карточку письма из текущей версии: запрос, основание, адресат и предпросмотр. Карточка протокола содержит встречу, версию, решения и список поручений с пропусками. Размер сообщений ограничивай. Длинный текст дели на страницы или сообщения, кнопки привязывай к одной управляющей карточке.
3. Для inline-кнопки передавай короткий непрозрачный токен запроса и код действия в пределах лимита Telegram. Из update передавай `callback_query.from.id` в `decide`. Видимость кнопки сама по себе не даёт права. Вызывай `answerCallbackQuery`, затем редактируй карточку или отправляй короткий статус. Ответы `already_decided`, `stale` и `forbidden` не создают внешних операций.
4. Для «На правку» заведи ограниченную по времени сессию редактирования, связанную с пользователем и исходной версией. Комментарий и исправления сохраняются в этом контексте. Передавай проверенную правку в `revise_document`. Новый текст или поля создают новую версию и запрос. Для сохранения постоянного правила используй отдельное явное действие через `save_preference`. Для протокола минимум нужен интерфейс, позволяющий инициатору поправить текст, исполнителя, срок или адресата с проверкой. Сначала можно дать текстовый ввод одного поля за шаг.

## PR 2. Планы и статусы

1. Включи `/plan YYYY-MM-DD` и `/week YYYY-MM-DD`, валидируй дату и разрешённый профиль. Если у пользователя два профиля, запроси выбор. Владелец workflow строит содержание плана. Ты отображаешь результат и доставляешь уведомление. Отправку в 08:30 запускает общий цикл по локальным правилам, ключ плановой отправки исключает повтор при рестарте.
2. Уведомляй отдельно о принятом решении и о результате внешних операций. Отклонение и возврат показывают окончание старой версии. Об ошибке сообщай, какое действие ждёт вмешательства. HTTP 429 обрабатывай по `retry_after`. Параллельный polling одного токена выявляй как конфигурационный сбой.
3. Совместная проверка: владелец тестового чата запускает бота, нажимает каждую кнопку, второй пользователь проверяет отказ. Основной репетиционный сценарий сохраняет отредактированную версию, а повторное нажатие не дублирует доставку.

## Критерии приёмки и передача

У основного сервиса есть записанный update и фактический Telegram ID. У планов есть понятные команда и формат. Тесты покрывают старую карточку, чужого актёра, повтор события, изменение версии при правке, ручной и плановый запуск и ошибку провайдера. На живой демонстрации видны реальные карточка и результат утверждения.

Перед закрытием PR отдельно проверь доставку плана дня и недели, плановый запуск и безопасный повтор отправки. В карточке частичного сбоя показывай, какие операции уже выполнены и какие ожидают повтора.
