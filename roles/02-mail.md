# 02. Почта и маршрутизация

[К командному плану](../TEAM_PLAN.md) · Стартовая ветка `feat/mail-routing`

**Результат.** Письмо принимается из тестового ящика, обрабатывается по правилам своего руководителя, типовой запрос доставляется, а чувствительный запрос ждёт решения.

## Что сделать

1. **Проверить живой канал.** В первый час принять письмо и отправить ответ между двумя тестовыми ящиками, начиная с Outlook. Зафиксировать наблюдаемый результат и блокер. Если Outlook технически недоступен, проверить допустимый сервис из ТЗ, например Яндекс. Стенд ограничить тестовыми получателями.
2. **Получить и нормализовать вход.** Использовать доступный и устойчивый для демо способ приёма. Сохранить ID провайдера, профиль, отправителя, тему, текст и время. Проверять повторы по профилю и внешнему ID. Роль отправителя определять по адресной книге и правилам, учитывая неизвестные контакты. Описать, откуда берётся профиль сообщения.
3. **Применить правила.** Начать с явных маршрутов. КП направить в продажи, жалобу — в сервис, статус — в сводку, неприоритетную рассылку — пропустить. Обычные внутренние встречи обрабатывать только при совпадении правила, после сверки свободного времени и защищённых блоков. Если правила противоречат друг другу или отправитель не определён, сохранить письмо для ручного решения.
4. **Поставить проверку перед отправкой.** Деньги и бюджеты, кадры, обязательства клиентам и письма руководству готовятся как черновик. Передать запрос владельцу Telegram через общий сервис. Сохранить выбранное правило и причину. Исполнитель ещё раз проверяет право, состояние, адресата и версию перед внешним действием.
5. **Подключить исходящую доставку.** Реализовать отправку для маршрутизации, утверждённых ответов и протоколов. По каждому получателю или согласованной неделимой операции хранить итог и внешний ID, когда он есть. Повтор доставки проходит через общую проверку операции. При неизвестном результате не отправлять вслепую.
6. **Оценить правила на 80 письмах.** Запустить классификацию и маршрутизацию без реальной рассылки. Исключить `expected_action` и `reason` из входа правил и модели. После прогона сопоставить предсказанное действие с эталоном и разнести промахи по классам. Отдельно проверить четыре чувствительные категории. Зафиксировать формулу доли автоматизации и различие между пакетной симуляцией и фактической доставкой на стенде.
7. **Связать сценарии.** Прогнать `m001` и `m002` через живую почту, передать статусное письмо владельцу планов, а отправку согласованного протокола проверить вместе с владельцем протокола.

## Что отдать команде

Основе — тип письма, ID, журнал и статус рассылки. Telegram — краткое основание, предлагаемое действие и ссылку на актуальный запрос решения. Планам — статусы, которые нужно показать в сводке. Для защиты — результаты 80 писем, разбивку ошибок и два наблюдаемых примера живого канала.

## Проверки

- У `m001` статус ожидания и отсутствует исходящая отправка. `m002` реально доставлено тестовому исполнителю. Жалоба, статус и рассылка дают ожидаемые маршруты.
- Для четырёх чувствительных категорий прямых действий до согласования нет. При неизвестном исходе отправки остаётся статус для сверки.
- Повтор входящего письма и повтор согласования не дублируют письмо. При частичном сбое повторяется только неуспешный получатель.
- В статистике есть все 80 строк, число совпадений, промахи по категориям и отдельный результат по чувствительным классам.
