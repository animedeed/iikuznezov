# ИИкузница. Как команде собрать первый рабочий цикл

Прототип «ИИ-помощник руководителя» помогает разобрать почту, подготовиться к дню и довести решения встречи до исполнителей. У каждого направления есть свой проверяемый результат. На общей репетиции результаты соединяются в один сценарий.

Исходный [PLAN.md в репозитории](https://github.com/animedeed/iikuznezov/blob/main/PLAN.md) задаёт объём. Этот документ раскрывает порядок работы. [AGENTS.md](AGENTS.md) содержит правила для агентов, а [настройки оркестрации](ORCHESTRATION.md) можно взять по желанию.

## Часть 1. Общий план для всей команды

### Что покажем

1. Руководителю приходит план дня в Telegram. В нём сегодняшние встречи, сроки, просрочки, итоги предыдущего рабочего дня и решения в ожидании. План недели собирается из тех же источников.
2. В тестовый ящик приходят два письма. По запросу КП помощник отправляет письмо тестовому исполнителю. Обязательство перед клиентом ждёт решения руководителя в Telegram.
3. На живой встрече аватар представляется ИИ-помощником, задаёт вопрос по прошлому протоколу и отвечает на новую реплику участника на русском. После встречи сервис получает текст разговора.
4. Инициатор получает протокол, исправляет одно поле и утверждает нужную версию. Участники получают письмо, исполнители — поручения. При необходимости создаётся событие в тестовом календаре. Повторное утверждение оставляет по одному результату.
5. Повторяемая правка видна в следующем черновике. Второй руководитель подключается через настройки и получает другой результат на том же типе письма.

### Первый час. Пять проверок доступа

| Проверка | Кто ведёт | Как понять, что можно продолжать |
| --- | --- | --- |
| Видеовстреча | Владелец аватара и второй участник | Аватар виден и слышен, отвечает на неожиданную реплику, текст разговора можно получить. Если первый сервис блокирует одну из этих операций, сразу проверить второй допустимый. |
| Почта | Владелец почты | Реальное письмо получено из тестового ящика, исходящее дошло до тестового адресата. Начать с Outlook, при блокере проверить допустимый запасной вариант. |
| Telegram | Владелец Telegram | Бот доставил карточку, владелец тестового чата нажал кнопку, сервис принял действие. Чужой Telegram-пользователь не может его выполнить. |
| Календарь | Владелец протокола и планов | Тестовая занятость читается, контрольное событие видно в подключённом календаре. |
| Данные и стенд | Владелец основы | У команды есть доступ к нужным исходникам и хостингу, стенд запускается, дата демо и тестовые контакты зафиксированы. |

К концу первого часа каждый сообщает итог в формате «проверил → наблюдал → следующий шаг». Запишите выбранные сервисы, кто владеет доступом, какие роли и адресаты используются в учебной встрече. Если драйвер или сервис сорвал проверку, укажите конкретную операцию и ответственного за запасной вариант. Остальные направления могут работать с согласованными синтетическими примерами. Статус живого канала выставляйте только после реального теста.

### В каком порядке соединяем работу

| Этап | Действия | Контрольная точка |
| --- | --- | --- |
| 1. Подключить каналы | Параллельно провести пять коротких проверок из таблицы. | Известно, что и на какой площадке можно показать вживую. |
| 2. Договориться о данных | Согласовать общие поля, хранение профилей, правила утверждения и примеры обмена. Загрузить тестовый профиль и исходные наборы. | Каждый владелец может запустить свой модуль на согласованном примере. |
| 3. Провести письмо до результата | Почта передаёт письмо в общую логику. Telegram получает карточку. В журнале видны правило, решение и итог. Протоколы и планы параллельно готовят план дня из запросов, задач и календаря. | `m001` ждёт руководителя, `m002` доставлен, утренний план виден. |
| 4. Провести встречу до поручений | Аватар передаёт текст, владелец протокола собирает черновик, Telegram доставляет его инициатору. После утверждения выполняются действия. | Правка есть в утверждённом протоколе. Тестовые получатели видят рассылку и задачи. |
| 5. Показать адаптацию | Сохранить повторяемую правку, подготовить следующий черновик, подключить второй профиль, прогнать один тип письма на обоих. | Изменение видно только там, где оно настроено. Данные профилей изолированы. |
| 6. Репетиция и сдача | Прогнать 80 писем, пройти сквозной сценарий, снять ролик, проверить форму, GitHub и доступность стенда. | Есть наблюдаемые результаты, замеры и честный список частично готовых мест. |

### Если работают четыре или три человека

| Размер команды | Расклад |
| --- | --- |
| Пять | По одному владельцу на каждое направление. Один из них ведёт общий прогон и сдачу. |
| Четыре | Совместить почту и Telegram у владельца интеграций. Основа, аватар, протокол и планы остаются отдельными направлениями. |
| Три | Первый ведёт основу, стенд и почту. Второй отвечает за Telegram, аватар и живую встречу. Третий ведёт протокол, календарь, задачи и планы. Для первого живого теста аватара нужен второй участник, даже если он закреплён за другим направлением. |

При составе меньше пяти раздайте роли по фактическим доступам и опыту. До объединения модулей можно распределить, кто подстрахует каждый внешний канал. Сначала выполните обязательный путь. Дополнительную пятничную сводку, справки о сотрудниках и автоматическое резервирование стратегических блоков берите после репетиции. Уже защищённые интервалы учитываются в обязательных переносах.

### Что проверяем перед сдачей

- **Разработчики и агенты.** Проверяют автоматические прогоны, версии согласований, полномочия, повторы событий, частичную доставку и изоляцию профилей. Отдельно анализируют ошибки по классам на всех 80 письмах. Для финансов, кадров, обязательств клиентам и писем руководству проверяют отсутствие действий до подтверждения.
- **Владельцы каналов.** Проверяют реальные доставки, разговор с неожиданной репликой, доступность стенда с другого устройства и запись события в тестовый календарь.
- **Вся команда.** Один раз репетирует полный путь на тестовых контактах. Проверяет, что видео доступно без авторизации, README позволяет запустить проект, а открытый GitHub содержит разрешённые материалы. Назначает человека, который проверяет форму и доступность стенда после сдачи.

В замерах отдельно покажите долю писем без решения руководителя, точность на 80 письмах, время от конца встречи до черновика и время согласования. Для недельной оценки используйте частоту операций × экономию активного времени человека. Укажите количество наблюдений и допущения. По исходной разметке 40 из 80 писем требуют решения. Ориентир 8–12 часов в неделю приведён в ТЗ как бизнес-цель.

По приложенному ТЗ первая репетиция назначена на 27 ноября 2026 года. Рабочий срок сдачи и запуска стенда — 28 ноября в 10:00 мск. В ТЗ указана отсечка формы и коммитов в 12:00 мск. Питч — 1 декабря. Стенд доступен до 3 декабря, 23:59 мск. До итогов 15 декабря его могут попросить поднять повторно в течение 24 часов. Ролик до трёх минут записывают одним фрагментом, без склеек, подмен и эффектов. Допускается ускорение ожидания ответа модели. Для сдачи нужны ссылка на видео без авторизации и HTTPS-ссылка на открытый Git-репозиторий с историей коммитов. Репозиторий держим открытым до объявления итогов. В README указываем запуск, настройку каналов, загрузку допустимых данных и шаги проверки. В форме явно перечисляем сделанное за 48 часов, частично готовые части и заглушки.

## Часть 2. Инструкции по направлениям

| Владелец | Открой инструкцию | Пример ветки |
| --- | --- | --- |
| Основа, профили и стенд | [01. Основа и стенд](roles/01-foundation.md) | `feat/profile-storage` |
| Почта и правила | [02. Почта и маршрутизация](roles/02-mail.md) | `feat/mail-routing` |
| Telegram и согласования | [03. Telegram](roles/03-telegram.md) | `feat/telegram-approval` |
| Видеовстреча и аватар | [04. Аватар](roles/04-avatar.md) | `feat/live-avatar` |
| Протокол, задачи, календарь и планы | [05. Протокол и планы](roles/05-minutes-calendar.md) | `feat/meeting-minutes` |

Ветки в таблице — образцы имён. На момент проверки GitHub в репозитории есть `main`. Создавайте ветку от актуальной `main`, когда берёте задачу. Владелец PR описывает результат и проверку. Короткие PR вносятся по мере готовности. Общие контракты и файлы согласуйте до параллельных изменений.

### Как взять задачу

1. Напишите в командном канале, какое направление берёте и какой результат будет в первом PR. Договоритесь с владельцем основы, если меняете общий формат данных.
2. Откройте свою копию репозитория в Codex. Проверьте состояние рабочей копии и обновите основную ветку. От неё создайте короткую ветку под задачу, например `feat/mail-routing`. Участники ведут свои ветки независимо.
3. Передайте Codex `AGENTS.md`, ссылку на свою инструкцию и конкретную цель первого PR. Например, «Прими одно тестовое письмо, запиши ID и профиль, повтор события не должен создать вторую запись».
4. Перед PR проверьте обычный путь и отказ или повтор, укажите команду или шаги проверки. Для живого канала приложите наблюдаемый итог без приватного содержимого. Согласуйте review с владельцем объекта, который потребляет ваш результат.

### Что согласовать между модулями

Имена полей ниже служат отправной точкой. Если в коде уже есть эквиваленты, используй существующие.

| Объект | Что передаём | Кто выдаёт → кто принимает |
| --- | --- | --- |
| Письмо | ID профиля и сообщения, отправитель и роль, тема, текст, время. Результат содержит правило, действие и причину. | Почта → общий сервис, планы, Telegram |
| Решение | ID профиля и объекта, версия, выданный сервисом ID запроса, уполномоченный пользователь, действие и время. | Общий сервис ↔ Telegram |
| Встреча | ID профиля и встречи, время, участники, повестка, контекст прошлой встречи и текст текущей встречи с меткой источника. | Основа и протокол ↔ аватар |
| Протокол и поручение | Версия, решения, открытые вопросы, участники. Для поручения нужны действие, исполнитель, срок и статус. Неизвестные обязательные поля помечаются для уточнения. | Протокол → Telegram и общий исполнитель |
| Внешнее действие | Уникальный ключ, целевой адресат или календарь, вид операции, статус, ошибка и внешний ID при наличии. | Общий исполнитель → почта, календарь или задачи |
| План | Профиль, дата и часовой пояс, период, встречи, сроки, просрочки, итоги, решения в ожидании. | Протокол и планы → Telegram |

Перед реализацией обменяйтесь одним валидным примером для каждого стыка и договоритесь, кто хранит первичную версию и кто ставит статус. Эталонные метки для оценки и исходные материалы рабочих встреч держите за пределами публичного Git.
