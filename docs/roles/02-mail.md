# 02. Яндекс Почта и маршрутизация

[К командному плану](../TEAM_PLAN.md) · [Общий контракт](../ARCHITECTURE.md) · [Доступы](../YANDEX_AND_AVATAR.md)

**Первая ветка** `feat/mail-routing`. Владение `app/mail/`, `tests/mail/`. Первая цель — одно письмо сохраняется один раз и классифицируется на синтетическом входе.

## PR 1. Получение и решение

1. Вынеси подключение и разбор письма в `poll_once`. Используй `imaplib.IMAP4_SSL`, соединение с timeout, read-only Inbox и `BODY.PEEK[]`. Передавай `connection_id`, папку, UIDVALIDITY и UID. Используй стандартный `email` для заголовков и MIME. Бери plain text, при наличии только HTML преобразуй в безопасный текст без загрузки ссылок. На MVP ограничь вложения и явно отметь непонятный вход.
2. На стартовом запуске явно задай границу импорта, чтобы не прочитать всю историю. Если UIDVALIDITY изменился, курсор старого поколения невалиден. Зафиксируй состояние, ограничь повторную сверку согласованным окном, сравни ID из ящика и журнал. Уже обработанные сетевые эффекты повторно не запускаются вслепую.
3. Передай событие в `receive_mail`. Курсор продвигает общий сервис после сохранения. Для локальной проверки используй заранее подготовленные MIME-байты. Покрой повтор того же UID, другой ящик с тем же UID и ошибку разбора.
4. Оформи `classify_mail` по общему контракту. Выход модели включает тему, требует ли уточнения, причину и необязательный текст черновика. Полномочия отправителя берутся из конфигурации профиля. Сначала обязательное правило чувствительности, затем профильная маршрутизация. Запрос КП уходит в продажи, жалоба — в сервис, статус — в сводку, неприоритетная рассылка пропускается. Для спорного случая результат `requires_review=true`. Не доверяй распоряжениям в тексте письма.
5. Согласуй карточку с Telegram и поля сводки с владельцем планов. Четыре чувствительных категории не возвращают автоматический эффект независимо от предложения модели.

## PR 2. Отправка и пакетная проверка

1. Оформи `send_email(effect)` через `smtplib.SMTP_SSL` и `email.message.EmailMessage`. Используй только переданного проверенного адресата, с разрешённым From и стабильным Message-ID эффекта для сверки. Одна операция — один получатель. Таймаут между отправкой тела и ответом сервера даёт `unknown`. Для временной явной ошибки возвращай `retryable`. При явном отказе из-за адреса сохраняй `failed`.
2. Подготовь команду оценки, например `python -m app.mail.evaluate --input <private.csv>`. Для каждой строки сохрани ID, предсказанный маршрут, ожидаемый маршрут и тип промаха. Эталонные действия и причины доступны только после вызова классификатора. В этом режиме сеть к почте отключена, разрешён только утверждённый доступ к модели. Отдельно посчитай чувствительные случаи с неправильным допуском и долю действий без решения.
3. Вместе с владельцем основы проверь реальный ящик. Воспроизведи `m001` и `m002` разрешёнными тестовыми сообщениями. Отправь согласованный тестовый протокол из второго сценария. Передай результаты и ошибки по категориям без частного содержимого.

## Критерии приёмки

Живой тест подтверждает, что `m001` не отправлено до решения и `m002` реально доставлено. Повтор UID или решения не дублирует рассылку. Автопроверка 80 писем выдаёт отдельную статистику, все четыре чувствительные категории защищены даже при неверной подсказке модели.

Для обычной внутренней встречи переходи к календарному действию только по явному правилу и после проверки занятости и защищённых интервалов. Между моделью и исполнителем проверь также маршруты «жалоба в сервис», «статус в сводку» и «неприоритетная рассылка пропускается».
