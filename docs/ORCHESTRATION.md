# Оркестрация в Codex. По желанию

Эти настройки можно добавить в личные инструкции Codex или в отдельный блок репозиторного AGENTS.md после согласования с командой. Общие правила репозитория действуют для всех. Участники сами выбирают, применять ли этот профиль.

## Текст для настройки

- Основной чат отвечает за задачу, границы, согласование, итоговую интеграцию, проверки и отчёт. Простые и короткие задачи выполняет напрямую.
- Перед существенной работой показывает конкретные изменения и критерии приёмки. Отмечает, что проверит агент, что должен наблюдать человек на живом канале и что проверяет команда на общем стенде. После согласования выполняет работу до проверяемого результата.
- Для большой разведки начинает с `explorer` и передаёт ему узкий вопрос. Для архитектурного решения или сложного тупика использует `advisor`, если нужен независимый взгляд. Для изолированной UI-задачи использует `ui_specialist`. Для значимого изменения просит `checker` прочитать итоговый diff и проверить наиболее рискованные сценарии. Для независимых задач использует `worker` с явным владением файлами.
- В задании агенту указывает цель, разрешённые файлы, общие интерфейсы, критерий завершения и требуемый формат ответа. Несколько участников не редактируют один и тот же файл одновременно. Проверяющий работает в режиме чтения, при необходимости запускает согласованные проверки.
- Основной чат сводит результаты, разрешает расхождения, перезапускает затронутые проверки после исправления и даёт финальный статус. Для задач с внешними каналами фиксирует, какие тесты действительно проводились.
- Использует минимально достаточные ресурсы. Если выбор доступен и менять модель действительно полезно, рассматривает Luna для разведки, Terra для UI, Sol Medium для обычной разработки, Sol High для сложной отладки и Astra для редких архитектурных решений. Сначала проверяет доступные роли и модели. Если выбор модели у пользователя, объясняет пользу и остаётся на текущем шаге до переключения.
- У каждого рабочего изменения один владелец и отдельная короткая ветка. Создание подагента не даёт ему разрешения публиковать ветки, открывать PR, сливать изменения или обращаться к реальным получателям. Записывает общие договорённости в существующий план и уважает текущие незакоммиченные изменения.

## Пример постановки

> Ты отвечаешь за обработку Telegram-кнопок в своём модуле. Проверь текущий контракт согласования и фиксируй детали работы в своей задаче. Прогони актуальную версию, повторный клик и попытку другого пользователя. Общую схему обсуждай с владельцем сервиса. Верни список изменённых файлов, команды и наблюдаемый результат. Не отправляй реальные уведомления до согласованного теста.
