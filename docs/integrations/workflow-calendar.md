## Протокол и утверждение

Основа уже принимает доверенный `MeetingSource` через `ApprovalService.submit_transcript(profile_id, source) -> str`. Результат — ID входного события. Один финальный источник на пару «профиль, встреча». Идентичный повтор возвращает тот же ID, изменённая расшифровка с тем же ID встречи вызывает конфликт. Инициатор, участники и допустимые исполнители берутся из доверенного источника. [Сервис согласований](../../app/core/approvals.py)

Обработчик входов предстоит подключить. Он передаёт генератору сохранённые реплики, время и название встречи из доверенного контекста, разрешённые контакты и явные предпочтения профиля. Генератор возвращает `MinutesCandidate`. Проверка перед записью сверяет встречу, ссылки на участников и исполнителей и ссылки `source_turn_ids` на `request_id` реплик этой встречи. Эталонный Summary используется при оценке. Поручение с отсутствующим исполнителем или сроком сохраняется с `null` и `needs_clarification`, а открытый вопрос поясняет, чего не хватает. Для вычисления даты из фразы используйте дату встречи и часовой пояс профиля. Неоднозначный срок требует уточнения.

Основа вызывает `ApprovalService.propose(profile_id, event_id, candidate, intents=...)` и получает `ApprovalCardView`. Для получения кандидата из `minutes_version` удалите `document_id`, `profile_id`, `version` и провалидируйте поля через `MinutesCandidate`. Первое предложение создаёт служебную Telegram-карточку инициатору. При правке `revise_document` принимает ожидаемую версию и открывает новую карточку. Только утверждение актуальной версии инициатором ставит деловые эффекты. На каждого разрешённого получателя рассылки передаётся отдельный `EffectIntent(kind=EffectKind.EMAIL, target_ref=participant_ref)`.

## Задачи

Основа уже принимает `EffectIntent(kind=EffectKind.TASK, target_ref=task_ref)` для поручения со статусом `draft`, заполненной датой и исполнителем из `allowed_assignee_refs`. При утверждении очередь получает `Effect` с `payload.task`, замороженным из версии протокола. Для `task-2` из примера эффект не создаётся. Код выдачи должен брать поручение из эффекта и сверять привязку исполнителя в профиле перед доставкой.

Пример тела `payload` задачи на границе `EffectTransport.execute`.

```json
{
  "task": {
    "task_ref": "task-1",
    "action": "Подготовить черновик КП",
    "assignee_ref": "sales-desk",
    "due_date": "2026-12-10",
    "status": "draft",
    "source_turn_ids": ["turn-1"]
  }
}
```

Предстоит подключить `publish_task(effect: Effect) -> EffectResult` к внутреннему хранилищу выданных поручений с `open` и `done`. Транспорт создаёт задачу по уникальной паре `(profile_id, effect.key)`, хранит исходный документ и версию, а при повторе возвращает существующий ID. Переход в `done` доступен подтверждённому исполнителю или руководителю того же профиля и фиксирует автора и время. Уведомление исполнителю, если настроено, имеет собственный статус доставки. Ошибка уведомления оставляет созданную задачу доступной.

## Календарь

`EffectKind.CALENDAR_EVENT` уже объявлен. Подготовку календарных эффектов, проверку конфликтов и CalDAV-транспорт предстоит реализовать. Чтение для плана и проверки занятости использует доверенную привязку коллекции к профилю. Адаптер принимает границы окна `[start, end)` с часовыми поясами, учитывает экземпляры повторяющихся и целодневных событий и возвращает активную занятость. Защищённые интервалы добавляются из настроек профиля. Для переноса сравнивается занятость целевого окна без переносимого экземпляра.

Предлагаемая форма календарного намерения в серверной версии. `calendar_ref` разрешается внутри профиля в конкретную коллекцию до утверждения. Для переноса нужны UID существующего события, идентификатор ресурса и сохранённый ETag. Ссылки на участников входят в утверждаемую запись.

```json
{
  "operation": "create",
  "calendar_ref": "demo-calendar",
  "uid": "demo-meeting-followup@example.invalid",
  "title": "Проверить черновик КП",
  "starts_at": "2026-12-10T11:00:00+03:00",
  "ends_at": "2026-12-10T11:30:00+03:00",
  "timezone": "Europe/Moscow",
  "participant_refs": ["sales-desk"]
}
```

Для выполнения адаптер реализует `upsert_event(effect: Effect) -> EffectResult`. Основа сохраняет параметры в версии, валидирует границы и часовой пояс, проверяет допустимые ссылки и помещает снимок утверждённой операции в эффект. Перед записью адаптер заново проверяет права, занятость, защищённые интервалы и актуальность ресурса. При изменении времени, коллекции или адресатов нужна новая версия. При создании используется условная запись по стабильному UID и пути ресурса, при изменении — условие по ETag. Если при повторе событие с этим UID совпало с утверждённым снимком, операция завершена. Занятость, расходящиеся данные или конфликт ETag требуют решения, с кодом причины в статусе эффекта. Таймаут после возможной записи даёт `unknown`. Сверка читает тот же ресурс, а при невозможности подтвердить исход операция передаётся оператору. Статусы рассылки и задач сохраняются независимо от календаря.

## План дня и недели

Предстоит подключить агрегатор `build_plan(profile_id, date, period) -> Plan` к календарю, задачам, результатам предыдущего рабочего дня, почтовым статусам и ожидающим согласованиям этого профиля. Часовой пояс берётся из `Profile`. День — локальные сутки, неделя — локальная календарная неделя с понедельника, предыдущий рабочий день считается по рабочему расписанию профиля. Просрочка — открытое поручение со сроком до даты запроса. Текущий `Plan` использует плоские списки, Telegram группирует недельный вывод по локальным датам начала встреч и `due_date` задач. Для такой группировки производитель заполняет `starts_at` у датированных встреч. Пример `plan_example` валидируется текущим `Plan`; для пустого окна возвращаются те же поля с пустыми списками. [Типы](../../app/contracts.py)

Для автоматической выдачи Telegram рабочий цикл планирования ставит один эффект на профиль, локальную дату и период в 08:30 локального времени. Ручной запрос привязывается к update ID. Сбой чтения источника отражается как ошибка получения данных, чтобы пустой план означал фактическое отсутствие записей.

## Приёмка

| Сценарий | Критерий |
| --- | --- |
| Синтетическая расшифровка → карточка → решение | Решение чужого пользователя запрещено. Старая версия устаревает после правки. Повтор принятого решения не порождает новых эффектов |
| Два поручения из примера | `task-1` выдаётся один раз, `task-2` остаётся на уточнение. В другом профиле поручения отсутствуют |
| Запись либо перенос | Повтор совпадающей записи возвращает её ID. Занятость, защищённый интервал или изменённый ETag блокируют запись |
| Частичная доставка | Сбой календаря оставляет результаты письма и задачи доступными. Неизвестный исход проверяется по UID |
| План | Понедельник показывает итоги предыдущего рабочего дня. Локальная полночь меняет окно по часовому поясу профиля. Повтор запуска расписания даёт одно сообщение |
| Живой канал | Контрольное событие читается обратно и видно в назначенном тестовом Яндекс Календаре. Утверждённая задача появляется в следующем плане Telegram |
