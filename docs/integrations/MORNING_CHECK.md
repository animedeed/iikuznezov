# Утренняя приёмка. ИИкузница

## 1. Проверить сборку перед живыми тестами

Запускайте из корня интеграционной ветки с Python 3.12. Первый запуск устанавливает библиотеки. Сам прогон использует синтетические данные и локальную SQLite.

```powershell
python -m venv .venv
$py = ".\.venv\Scripts\python.exe"
& $py -m pip install -e '.[test,calendar]'
& $py -m app.offline_demo
& $py -m pytest -q
```

На Linux используйте `.venv/bin/python`. Офлайн-отчёт должен содержать `mode: offline` и `external_calls: 0`. Проверьте, что `m001` прошёл после согласования, `m002` прошёл автоматически, у встречи сохранился один черновик, созданы одна полная задача и одна запись календаря. В прогоне имитируется временный отказ календаря. Письма и задача при этом завершаются, а календарь выполняется при безопасном повторе. Один повтор плана на ту же дату не создаёт второе уведомление.

## 2. Живые проверки по каналам

1. **Яндекс Почта.** Владелец проверяет тестовые адреса, создаёт пароль приложения типа «Почта» и задаёт `YANDEX_MAIL_ADDRESS`, `YANDEX_MAIL_APP_PASSWORD`. Проверяет SMTP командой `python -m app.mail --to <тестовый-получатель>` и смотрит, дошло ли письмо во второй ящик. Проверка получения зависит от IMAP-обработчика владельца. Точка входа основы для него — `process_mail(store, channel_id, receipt, candidate, sales_alias=..., trusted_quote=...)`. `channel_id` и `sales_alias` берутся из доверенной конфигурации. `trusted_quote=True` выставляется по результату независимой проверки доверенным правилом. Деловое действие выполняет очередь. [Почтовый модуль](../../app/mail/README.md) · [Контракт](mail.md)
2. **Видеовстреча.** Владелец проверяет реальный звонок и речь на двух устройствах. Серверные `start`, `turns` и `finish` уже принимают временный токен встречи. Локальный сценарий выдачи токена приведён ниже. На реальном стенде аватар передаёт услышанные реплики в те же endpoints. После `finish` вызывается контролируемый проход обработки сохранённых встреч. [HTTP-контракт встречи](meeting.md) · [Яндекс и аватар](../YANDEX_AND_AVATAR.md)
3. **Модель и протокол.** Владелец задаёт `YANDEX_LLM_API_KEY` и `YANDEX_FOLDER_ID` в окружении стенда. `YANDEX_LLM_MODEL` по умолчанию `yandexgpt-5.1`. После сохранения живой расшифровки запускает `python -m app process-meetings --profile-id <профиль>` и проверяет черновик. Повтор запрашивает только необработанные события. При ошибке модели исходная расшифровка остаётся для следующего запуска. [Контракт протокола](workflow-calendar.md)
4. **Яндекс Календарь.** Владелец задаёт `YANDEX_CALDAV_EMAIL` и `YANDEX_CALDAV_KEY` для выделенного календаря. Сначала `python check_calendar.py --list`, затем `python check_calendar.py <имя-календаря>` с проверенным названием. Команда записывает учебное событие. Проверьте его в интерфейсе календаря и отметьте, что повтор с тем же UID не создал второе. [Проверочная команда](../../check_calendar.py) · [Контракт календаря](workflow-calendar.md#календарь)
5. **Telegram.** Владелец Telegram использует [команду интеграционного запуска m001](../../README.md#интеграционный-запуск-m001). Ему нужны тестовый бот, разрешённый тестовый чат, ID согласующего и доступы SMTP из пункта 1. В живом прогоне необходимо подтвердить отдельно ответ на кнопку и отчёт о доставке. Плановый эффект `plan_message` формируется локально. Его отправка через общий Telegram-адаптер остаётся задачей владельца канала. [Контракт Telegram](telegram.md)

Названия переменных и пример команд можно публиковать. Значения ключей, пароли, токен встречи, закрытые ссылки и содержимое рабочих данных остаются в окружении или закрытом журнале.

### Тестовая HTTP-сессия встречи

Используйте одну отдельную SQLite для сервера и CLI. Согласующий здесь синтетический, почта и бот не нужны.

```powershell
$env:IIKUZNEZOV_DB = "data/meeting-check.sqlite3"
& $py -m app seed-demo
& $py -m app provision-meeting --profile-id demo-p1 --meeting-id demo-meeting --initiator-id 10001 --participant-ref sales-desk --assignee-ref sales-desk
& $py -m uvicorn app.main:app --workers 1
```

Вызовите три маршрута из [HTTP-контракта](meeting.md) через локальный клиент. Перенесите выпущенный токен в Authorization только для этой сессии. В отсутствие ключей модели ответы аватара детерминированы. После `finish` источник можно обработать командой `process-meetings` с настроенной моделью. Для полной проверки без ключей используйте `python -m app.offline_demo`. Для нового прогона выберите новый ID встречи.

## 3. Заполнить результат

Пишите «прошло», «сбой» или «не запускали». Указывайте время, владельца и наблюдаемый результат без секретов. Если внешний сервис недоступен, запишите конкретную операцию, на которой остановились.

| Проверка | Ожидаемый результат | Факт, время, владелец |
| --- | --- | --- |
| Офлайн-прогон | `external_calls: 0`, почта, протокол, задача, календарь и план | |
| Реальная отправка SMTP | Получено одно письмо на втором тестовом ящике | |
| IMAP и входящие `m001`, `m002` | Источник зарегистрирован один раз. `m001` ждёт решения, `m002` проходит по правилу | |
| Живой Телемост и SpeechKit | Второй участник слышит ответ на новую реплику, финальный текст дошёл до API | |
| Модель и протокол | Черновик сохранён для нужного профиля. Зафиксировано время от завершения встречи | |
| Яндекс Календарь | Видна одна учебная запись, повтор использует тот же UID | |
| Telegram и статус доставки | Решение и состояние доставки видны отдельно, повтор не создаёт новое письмо | |

При сдаче разделяйте наблюдения офлайн и на живых каналах. Готовность стенда к питчу подтверждается только публично доступным по инструкции запуском и сквозным прогоном на согласованных тестовых аккаунтах.
