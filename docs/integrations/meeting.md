# Видеовстреча и аватар

[Архитектура](../ARCHITECTURE.md) · [Роль владельца](../roles/04-avatar.md) · [Настройка тестовой комнаты](../YANDEX_AND_AVATAR.md)

В основе доступны модели `MeetingTurn`, `MeetingReply` и `ApprovalService.submit_transcript(profile_id, source: MeetingSource) -> str`. Последний сохраняет финальный текст как входящее событие `meeting`. HTTP-маршруты ниже, выдача токена, сохранение живых реплик и фоновая обработка финального события требуют реализации.

## Граница клиента и сервиса

Оператор входит в тестовую комнату. Клиент аватара управляет камерой, звуком, STT и TTS. Он передаёт только финальный текст распознанной реплики. Перед озвучкой клиент закрывает окно прослушивания, чтобы собственная речь аватара не попала во вход. Частичные гипотезы STT остаются у клиента. Если речь не распознана, клиент просит повторить. Сбой TTS оставляет сохранённые реплики доступными для протокола.

Администратор создаёт сессию закрытой CLI-командой. Сессия привязана к профилю, встрече, инициатору, участникам и разрешённому контексту предыдущего протокола. Клиент передаёт временный токен в заголовке `Authorization: Bearer <session_token>` по HTTPS. Сервис хранит хеш токена, проверяет срок и связь с ID встречи в пути. Предлагаемый TTL тестовой сессии — 30 минут, параметр стенда. Профиль, инициатор и роли в протоколе определяются на сервере. Текст реплик используется как вход для модели. Ответ ассистента может предложить действие, а чувствительный запрос помечается для решения руководителя. Создание задачи, изменение календаря и отправка письма проходят через согласование соответствующего сценария.

## HTTP-контракт v1

Все пути начинаются с `/v1/meetings/{meeting_id}`. Пример ниже описывает последовательный прогон для синтетической встречи `demo-meeting`. Объекты `request` и `response` содержат соответствующие тела запросов и ответов.

```json
[
  {
    "method": "POST",
    "path": "/v1/meetings/demo-meeting/start",
    "request": {"request_id": "start-1"},
    "status": 200,
    "response": {"reply_text": "Я ИИ-помощник. Что осталось по поставке?"}
  },
  {
    "method": "POST",
    "path": "/v1/meetings/demo-meeting/turns",
    "request": {
      "request_id": "turn-1",
      "sequence": 1,
      "text": "В четверг можем отправить черновик КП.",
      "role": "participant"
    },
    "status": 200,
    "response": {
      "sequence": 1,
      "reply_text": "Кто подтвердит срок?",
      "approval_required": false
    }
  },
  {
    "method": "POST",
    "path": "/v1/meetings/demo-meeting/finish",
    "request": {"request_id": "finish-1"},
    "status": 202,
    "response": {"status": "queued", "meeting_id": "demo-meeting"}
  }
]
```

- `start` открывает встречу и сохраняет приветствие. `turns` принимает одну реплику за раз. Клиент нумерует входящие реплики с единицы и сохраняет ID запроса для повтора. Ответ модели имеет тот же номер. Отдельные записи реплик ассистента формирует сервер. При сбое модели сервер сохраняет входную реплику и выдаёт нейтральный ответ. Состояние незавершённого вызова восстанавливается после рестарта.
- `finish` вызывается после подтверждения последней реплики. Сервер закрывает приём новых реплик и фиксирует из сохранённых записей один финальный вход для генератора протокола. Подтверждение `202 queued` означает, что работа сохранена. Черновик и карточка согласования появляются после обработки. Повтор завершения той же встречи с новым ID возвращает тот же итог без второй работы.
- В пределах сессии `request_id` уникален. Вместе с ним хранятся маршрут и тело запроса. Идентичный повтор с действующим токеном возвращает сохранённый результат, в том числе после рестарта. Если первый запрос ещё обрабатывается, сервер возвращает `409` с кодом `request_in_progress`. Клиент повторяет тот же ID после паузы. ID с изменившимся телом или маршрутом, пропуск порядкового номера и новая реплика после закрытия дают `409`. Для отсутствующего, истёкшего, неизвестного или привязанного к другой встрече токена сервер выдаёт одинаковый `401`. Некорректная схема даёт `422`. При временной недоступности сервиса возвращается `503`. Тело ошибки содержит `code` и `message`, журнал ограничивается безопасным кодом и ID корреляции. `MeetingTurn` принимает роль `participant`, положительный номер и текст длиной от 1 до 100 000 символов после удаления крайних пробелов. Неизвестные поля отклоняются.

## Передача протоколу

После авторизации доверенный обработчик строит `MeetingSource(meeting_id, initiator, participant_refs, allowed_assignee_refs, turns)`. `initiator` имеет тип `TelegramActor`. `turns` содержит кортеж `TranscriptTurn` с `request_id`, `sequence`, `text` и ролью `participant` или `assistant`. Сервер присваивает каждой записи финального журнала собственный уникальный ID и порядковый номер. Номер финальной записи может отличаться от номера входящего HTTP-запроса. Ссылки на фрагменты протокола используют ID этих записей. Доверенный импорт учебной расшифровки передаёт тот же тип напрямую после привязки к профилю.

`submit_transcript` возвращает `event_id`. Повтор с тем же профилем, ID встречи и содержимым возвращает существующий ID. Для другого финального текста с этой же парой профиль–встреча сервис выдаёт `ValueError`. Перед вызовом обработчик уже обязан проверить полномочия. Инициатор утверждает версию протокола через Telegram.

## Приёмка

- **Синтетическая.** С подставной моделью проиграть три запроса по порядку. Повторить последнюю реплику после рестарта, затем дважды завершить встречу с разными ID. Проверить одну финальную расшифровку, одно входящее событие и сохранённый ответ. Отдельно проверить чужую встречу, истёкший токен, неверную схему, нарушенную последовательность и сбой модели. Ближайшая проверка готовой основы — `test_meeting_initiator_only_and_incomplete_task_never_queued` в `tests/core/test_approvals.py`.
- **Живая.** На двух устройствах подтвердить, что участник видит аватар и слышит ответ на неожиданную фразу. Провести минимум два обмена, измерить задержку от конца реплики до первого звука и сверить попадание содержательных фраз в черновик. Для приёмки нужны согласованная тестовая комната, настольный клиент и доступы STT, TTS и модели.
