# Почта и правила маршрутизации

## Приём письма

Почтовый адаптер читает IMAP-папку в режиме read-only через `BODY.PEEK[]` и разбирает MIME в нормализованные поля. Для HTML без plain text извлекает текст без сетевых запросов. Для первой синхронизации оператор задаёт границу импорта. Блокирующие вызовы IMAP и SMTP выполняются вне event loop с таймаутом.

Действующий стык `Store.receive_mail(channel_id, receipt: MailReceipt) -> ReceiptResult`. `channel_id` берётся из доверенной настройки подключения. Основа по активной привязке определяет профиль и сохраняет вход. `received_at` должен содержать смещение или `Z`. В JSON поле отправителя называется `from`. `fixture_id` и `channel_id` из общих фикстур вынесены из модели.

Ключ повтора состоит из подключения, папки, UIDVALIDITY и UID. Первый вызов возвращает `duplicate=false`, повтор — тот же `event_id` и `duplicate=true`. Неизвестная или отозванная привязка даёт `LookupError`. По одному UID на разных подключениях сохраняются независимые события. После сохранения входа адаптер может продвинуть курсор. После смены UIDVALIDITY адаптер начинает сверку в ограниченном окне и проверяет предыдущие доставки перед возможной повторной обработкой. При ошибке MIME вход остаётся доступен для повторного разбора или отдельной операторской отметки.

Пример вызова. Внутренний `event_id` для демонстрации условный.

```json
{
  "channel_id": "demo-mail-sales",
  "receipt": {
    "folder": "INBOX",
    "uidvalidity": 42,
    "uid": 101,
    "from": "customer@example.invalid",
    "subject": "Подтверждение срока поставки",
    "text": "Можете гарантировать поставку в эту пятницу?",
    "received_at": "2026-12-07T07:00:00Z"
  },
  "first_result": {
    "event_id": "demo-mail-event-101",
    "profile_id": "demo-p1",
    "duplicate": false
  },
  "replay_result": {
    "event_id": "demo-mail-event-101",
    "profile_id": "demo-p1",
    "duplicate": true
  }
}
```

## Классификация и постановка операции

Стык `classify_mail(mail, context) -> MailCandidate` предстоит подключить в `app/mail/`. Основа передаёт сохранённое письмо и минимальный контекст его профиля. Модель возвращает `topic`, `requires_review`, `rationale`, необязательные `policy_class` и `draft_text`. Правило, разрешение на внешнюю операцию, адресат и согласующий определяются на сервере. Инструкции из письма и эталонные поля оценочного набора не участвуют в проверке полномочий.

Сервер сначала применяет обязательные правила для `finance`, `hr`, `customer_commitment` и `executive_mail`. Эти классы и неоднозначные случаи идут руководителю. Остальные маршруты берутся из настроек профиля: `forward_sales`, `forward_service`, `record_status`, `ignore`, `review`, `check_calendar`. Для календарного изменения нужен явно разрешающий маршрут и проверка доступности интервала. Для автоматического эффекта нужны явное разрешение профиля и включённая автоматизация среды.

Действующий путь ручного решения вызывает `ApprovalService.propose(profile_id, event_id, candidate, mail_dispatch=..., intents=...)`. `MailDispatch` фиксирует действие и доверенную ссылку получателя в версии. Сервис атомарно открывает согласование и сохраняет служебный Telegram-эффект. Деловой эффект для `forward` или `reply` появляется только после `approve`, текст ответа берётся из версии. При `reject` или `revise` доставка не ставится. Правка содержимого или адресата требует новой версии и нового согласования. Для ручной карточки без заранее определённой операции список `intents` может быть пустым.

Входная очередь, фоновый вызов классификатора и автоматическая ветка соединяются следующим шагом. Для автоматической ветки завершение входа, версия/решение правила и очередь должны записаться одной транзакцией. Повтор задания переиспользует сохранённый результат, сбой модели оставляет вход доступным для обработки. `propose` открывает ручное согласование и само по себе автоматический маршрут не исполняет.

Ожидания для сценариев ниже применяются после реализации маршрутизатора. Число эффектов учитывает только деловые операции.

```json
[
  {
    "fixture_id": "m001",
    "profile_id": "demo-p1",
    "route": "review",
    "policy_class": "customer_commitment",
    "approver_role": "leader",
    "action_effects_before_approval": 0
  },
  {
    "fixture_id": "m002",
    "profile_id": "demo-p1",
    "route": "forward_sales",
    "target_ref": "sales-desk",
    "action_effects_before_approval": 1
  },
  {
    "fixture_id": "m002",
    "profile_id": "demo-p2",
    "route": "review",
    "approver_role": "leader",
    "action_effects_before_approval": 0
  }
]
```

В сценарии `m002` для `demo-p2` передать те же данные письма через привязку `demo-mail-review`. Ожидания читать только после классификации. В режиме пакетной оценки исключить отправку и запись эффектов в стенд.

## Доставка

Почтовый транспорт реализует `send_email(effect: Effect) -> EffectResult` для очереди `EffectQueue.run_once(transport)`. Эффект несёт профиль, версию или источник, ключ, ссылку одного получателя и зафиксированный payload. Для действия над письмом текущий payload включает `action`, `source_id`, `draft_text`. Для рассылки протокола текущее тело строится из `payload.minutes` утверждённой версии.

До включения SMTP основа должна закрепить адрес получателя за версией операции и проверять доступ и привязку отправителя перед доставкой. Текущий `MailDispatch` закрепляет `target_ref`. Если конфигурация ссылки изменилась, старый эффект не перенаправляется на новый адрес. Один эффект — один адресат. У повторов общий стабильный Message-ID, полезный для сверки у провайдера.

| Результат транспорта | Действие очереди |
| --- | --- |
| `sent` | SMTP принял сообщение. Сохранить безопасный внешний идентификатор, если он доступен |
| `retryable` | Явный временный отказ до подтверждённого приёма. Повторить ограниченное число раз с тем же ключом |
| `unknown` | Возможна отправка, например при разрыве после передачи тела. Сначала сверить доставку или передать оператору |
| `failed` | Явный постоянный отказ, например невозможность доставки на адрес. Сохранить безопасный код |

```json
{
  "status": "unknown",
  "error_code": "smtp_response_lost"
}
```

## Приёмка

- В основе проверяются `test_mail_replay_and_uid_validity`, `test_replaced_mail_binding_is_inactive_and_cannot_move_profile` и `test_callback_persists_version_actor_comment_and_one_effect`.
- После сборки адаптеров проверить синтетическое MIME-письмо через весь стык, повтор в том же и в другом подключении, рестарт после сохранения входа, отсутствие деловой операции до решения по `m001`, оба профиля для `m002`, а также обязательный контроль всех четырёх чувствительных классов. Проверить недоступность письма из чужого профиля и потерю SMTP-ответа без повторной отправки.
- На выделенных ящиках проверить реальное чтение без изменения флагов и доставку `m002` тестовому получателю. Для `m001` зафиксировать отсутствие отправки до согласования и фактическую доставку после утверждения. Живой прогон проводит владелец канала с разрешёнными ящиками.
