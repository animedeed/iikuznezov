# Telegram. Карточки, решения и планы

[Архитектура](../ARCHITECTURE.md) · [Роль владельца](../roles/03-telegram.md) · [Настройка канала](../YANDEX_AND_AVATAR.md)

В `6fb5a92` основа уже хранит версии, решения и служебные уведомления в SQLite. `ApprovalPort` объявляет `decide`. Чтение карточки и решения, сохранение правки и предпочтения доступны через `ApprovalService`. Владелец Telegram реализует `poll_updates`, `handle_update` и `notify` в `app/telegram/`. Подключение циклов, хранилище входящих updates и курсора, а также доверенная привязка бота, Telegram-пользователя и чата нужны для интеграции. В текущем `bindings` Telegram ID руководителя сохраняется отдельно от этой будущей маршрутизации.

**Отправка карточки.** `propose` атомарно открывает запрос и создаёт служебный `Effect` с `kind=telegram`, `payload.operation=approval_notice` и `target_ref=approval_id`. Исполнитель перед отправкой вызывает `get_pending(effect.profile_id, effect.target_ref, TelegramActor(telegram_user_id=…))`. Пользователь берётся из сохранённого эффекта, чат — из подтверждённой конфигурации. Отправка требует обеих проверок. `get_pending` возвращает `ApprovalCardView` со снимком именно этой версии либо `None`. При `None` вызов Bot API пропускается. Очередь сама отменяет известные закрытые карточки до захвата. Если карточка стала недоступна после захвата, текущий `EffectResult` позволяет вернуть `failed` с безопасным кодом `approval_unavailable`, чтобы остановить повторы. Состояние `cancelled` существует в очереди и пока отсутствует среди результатов транспорта.

Пример входа транспортного адаптера `notify`. Идентификаторы синтетические.

```json
{
  "effect_id": "notice-1",
  "profile_id": "demo-p1",
  "key": "approval-notice:0123456789abcdef0123456789abcdef",
  "kind": "telegram",
  "target_ref": "0123456789abcdef0123456789abcdef",
  "document_id": "demo-mail-draft",
  "version": 1,
  "payload": {
    "operation": "approval_notice",
    "telegram_user_id": 10001
  }
}
```

Карточка показывает версию, основание решения и предпросмотр, адресата письма либо участников и поручения протокола. Неизвестные поля поручений отмечаются явно. Кнопки привязываются к одной управляющей карточке. Предлагаемый код кнопки для текущих 32-символьных ID — `a:<approval_id>:<approve|reject|revise>`, до 64 байт UTF‑8. Обработчик валидирует форму и действие, находит контекст отправленной карточки по боту, чату и `message_id`, сверяет из него ID запроса и берёт ID пользователя из `callback_query.from.id`. При нескольких профилях контекст карточки задаёт одну привязку и повторно проверяется перед вызовом сервиса. Профиль, версия, текст, получатель и эффекты разрешаются на сервере по ID запроса и сохранённому снимку.

Пример update от подставного Bot API. Чат и пользователь в примере синтетические. Для живого канала значения берутся из доверенной привязки.

```json
{
  "update_id": 720001,
  "callback_query": {
    "id": "cb-test-1",
    "from": {"id": 10001, "is_bot": false, "first_name": "Тест"},
    "message": {
      "message_id": 31,
      "date": 1796626800,
      "chat": {"id": 10001, "type": "private", "first_name": "Тест"},
      "text": "Письмо ждёт решения · версия 1"
    },
    "chat_instance": "test-chat-instance",
    "data": "a:0123456789abcdef0123456789abcdef:approve"
  }
}
```

**Решение.** Для валидного события обработчик передаёт в `ApprovalPort.decide(approval_id, actor, decision, comment=None)` только ID запроса, `TelegramActor` и `Decision`. Комментарий передаётся из проверенного контекста редактирования, если он уже введён. Сервис проверяет сохранённого адресата запроса, для руководителя — актуальность его привязки, для протокола — ID инициатора встречи. При асинхронном polling синхронный вызов SQLite выполняется вне event loop.

| Результат | Ответ через `answerCallbackQuery` и состояние |
| --- | --- |
| `accepted` при `approve` | Показать «Решение принято». В базе сохранены версия, автор и время, деловые эффекты поставлены один раз. Итог доставки отображается по каждому эффекту отдельно. |
| `accepted` при `reject` или `revise` | Закрыть кнопки и показать «Отклонено» либо «На правку». Деловых эффектов нет. После `revise` доступен ввод правки. |
| `already_decided` | Показать, что запрос уже решён. Сохранённое решение можно восстановить через `get_decision(profile_id, approval_id, actor)` после проверки контекста. |
| `stale` | Показать, что карточка устарела. Новая версия продолжает ждать решение. |
| `forbidden` | Показать общий отказ без сведений о запросе или профиле. |
| `validation_error` или неверный формат кнопки | Показать ошибку действия без изменений в базе и очереди деловых эффектов. |

`answerCallbackQuery` вызывается и для отказов. Сбой подтверждения в Telegram не отменяет записанное решение. В плане дня и карточке частичной доставки показываются наблюдаемые статусы каждого действия. При явном HTTP 429 транспорт отдаёт `retryable` и `retry_after_seconds`. Подтверждённая отправка возвращает `sent` и строковый `external_id` сообщения. Таймаут с неизвестным исходом возвращает `unknown`, затем требуется сверка перед повтором.

**Правка.** Сессия ввода ограничена по времени и привязана к пользователю, чату, профилю, документу и исходной версии. Проверенная правка преобразуется на сервере в полный `Candidate` и новые доверенные параметры доставки. Вызов основы — `revise_document(profile_id, document_id, actor, expected_version, candidate, mail_dispatch=…, intents=…)`. Успех открывает новый запрос, старая кнопка возвращает `stale`. Если деловая доставка уже началась, исходная версия сохраняется, а исправление оформляется отдельным документом. `save_preference` вызывается по отдельному явному действию руководителя.

**Приём событий и планы.** Один процесс делает long polling на токен. Сначала надёжно записать update по паре `(bot_id, update_id)`, затем продвинуть курсор. После рестарта обработать незавершённые updates. Повтор update и два нажатия проверяются независимо. Команды `/plan YYYY-MM-DD` и `/week YYYY-MM-DD` валидируют дату и доступ, при нескольких разрешённых профилях запрашивают явный выбор, затем передают `day` или `week` в `build_plan(profile_id, date, period)` и отображают `Plan`. Ручной ответ привязан к update. У планового уведомления отдельный ключ по профилю, локальной дате и периоду. Общее расписание вызывает владельца workflow и передаёт результат в Telegram для доставки.

**Приёмка.** С подставным Bot API запустить фактический обработчик Telegram с `ApprovalService` и одной временной SQLite. Провести по отдельной карточке через каждую кнопку. Проверить попытку чужого пользователя и чата, старую версию после правки, повтор update, повтор решения после рестарта и отказ отправки. Сверить один деловой эффект для утверждения и ноль для отклонения и возврата. Для планов проверить ручной запрос, два профиля, плановый запуск и повтор после рестарта. На выделенном стенде проверить `sendMessage → нажатие → callback → answerCallbackQuery` и итоговый статус в чате. Текущие `tests/core/test_approvals.py` и `tests/core/test_effects.py` покрывают сервис и очередь. Полный прогон требует адаптера Telegram и подтверждённого чата.
