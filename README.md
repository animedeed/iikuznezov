# ИИкузница

Прототип ИИ-помощника руководителя. [Командный план](docs/TEAM_PLAN.md) · [Архитектура](docs/ARCHITECTURE.md) · [Контракты подключения](docs/integrations/README.md) · [Настройка каналов](docs/YANDEX_AND_AVATAR.md).

Эта ветка содержит основу, сохранение согласований Telegram и очередь действий. Для запуска нужны Python 3.12 и зависимости из `pyproject.toml`. Почта, Telegram и облачные ключи для локальной проверки не нужны.

## Запуск

```powershell
python -m venv .venv
.\.venv\Scripts\python -m pip install -e '.[test]'
.\.venv\Scripts\python -m app seed-demo
.\.venv\Scripts\python -m app smoke
.\.venv\Scripts\python -m pytest -q
.\.venv\Scripts\python -m uvicorn app.main:app --workers 1
```

На Linux используйте `.venv/bin/python` вместо `.\.venv\Scripts\python`. В другом окне проверьте `GET http://127.0.0.1:8000/health`. Ответ — `{"status":"ok"}`.

По умолчанию SQLite находится в `data/iikuznezov.sqlite3`. Укажите переменную окружения `IIKUZNEZOV_DB` до запуска, чтобы использовать другой файл. `.env.example` перечисляет настройки, приложение читает переменные процесса. Для демо используйте отдельный файл базы. Миграция применяется при запуске API и CLI. `seed-demo` создаёт два профиля с разными правилами для КП. `smoke` регистрирует одно синтетическое письмо, сохраняет первую версию черновика и подтверждает дедупликацию и изоляцию. Повтор smoke использует то же письмо и черновик. Замена почтовой привязки отключает прежний вход и сохраняет её принадлежность профилю.

## Контракт v1

### Тестовый Telegram-бот

Используйте отдельного бота от `@BotFather`. Отправьте ему `/start` в личном чате. Для проверки с двумя пользователями добавьте бота в отдельную тестовую группу и отправьте там `/start@имя_бота`.

```powershell
$env:TELEGRAM_BOT_TOKEN = Read-Host 'Токен тестового бота' -MaskInput
.\.venv\Scripts\python -m app.telegram --get-me
.\.venv\Scripts\python -m app.telegram --identify
.\.venv\Scripts\python -m app.telegram --user-id 123456789
```

Подставьте `user-id` согласующего из вывода `--identify`. Для проверки отказа в группе добавьте `--chat-id` с ID этой группы. Сначала нажмите кнопку со второго аккаунта, затем с аккаунта согласующего. Для проверки правки выберите «На правку» и в течение 10 минут отправьте `/revise Новый текст письма` в личном чате с ботом.

Для живой проверки в закрытой тестовой группе отправьте в ней `/start@имя_бота`, пока работает `--identify`. Подставьте полученные ID. Именованный прогон открывает свежую карточку в отдельной базе и проверяет привязку кнопки к отправленному сообщению.

```powershell
.\.venv\Scripts\python -m app.telegram --user-id 123456789 --chat-id=-1001234567890 --run-id group-approve
```

Проверьте «Утвердить» сначала со второго аккаунта, затем с аккаунта согласующего. Для «Отклонить» остановите процесс и повторите запуск с `--run-id group-reject`. После отклонения строка о пробной отправке письма появиться не должна.

Демо использует отдельную SQLite-базу в `data/`. Утверждение запускает имитацию отправки письма, результат виден в консоли. Запускайте один процесс на тестовый токен. Если нужен новый прогон, остановите процесс и переименуйте каталог базы, указанный при запуске.

Для согласования протокола остановите демо письма через `Ctrl+C` и запустите второй сценарий с тем же ID:

```powershell
.\.venv\Scripts\python -m app.telegram --user-id 123456789 --scenario minutes
```

Нажмите «На правку» и отправьте одну команду в личном чате с ботом. После каждой принятой правки придёт новая карточка. Чтобы изменить ещё одно поле, откройте «На правку» на новой версии.

| Поле | Пример |
| --- | --- |
| Итог встречи | `/revise summary Команда согласовала перенос поставки.` |
| Текст поручения | `/revise task Сообщить клиенту новый срок.` |
| Исполнитель | `/revise assignee demo-maria` |
| Срок | `/revise due 2026-12-08` |
| Адресат протокола | `/revise recipient demo-manager` |

Тестовые исполнители — `demo-alex` и `demo-maria`. Тестовые адресаты — `demo-team` и `demo-manager`. После утверждения консоль покажет имитацию отправки протокола. Если у поручения есть исполнитель и срок, консоль также покажет имитацию его создания.

После сообщения «Утверждено» бот отдельно пришлёт «Результат выполнения» со статусом каждой операции. При временном сбое результат показывает, что уже выполнено и что ожидает повтора. После завершения повтора приходит обновлённый результат. Демо проводит операции через тестовый транспорт.

Чтобы сохранить постоянное правило тестового профиля, отправьте в личном чате `/remember Сначала указывай срок поставки`. Команда доступна руководителю профиля, а повтор с тем же текстом не создаёт копию правила. Обычные правки через `/revise` меняют версию документа. Правила хранятся в SQLite текущего сценария и доступны общему сервису согласований. Демо-карточки используют заранее заданный текст.

Когда запущен любой из двух сценариев, согласующий может запросить синтетические планы в личном чате с ботом:

- `/plan 2026-12-07` — план дня.
- `/week 2026-12-07` — семь дней начиная с указанной даты.

Оба плана включают встречи, задачи к сроку, просрочки, итоги предыдущего рабочего дня, статусы писем и ожидающие согласования. Встречи показаны по московскому времени. Демонстрационный провайдер использует тестовые записи.

Для автоматической доставки плана в личный чат включите `--morning-plan` при запуске демо. Процесс должен работать в 08:30 по Москве. При более позднем запуске пропущенная отправка не создаётся.

```powershell
.\.venv\Scripts\python -m app.telegram --user-id 123456789 --scenario minutes --morning-plan
```

Чтобы проверить доставку сразу, остановите текущий процесс и выполните команду ниже. Она отправляет сегодняшний план и выходит. Повтор команды использует тот же ключ доставки. Если план уже отправлен, второй экземпляр не придёт. При успешной отправке оставшийся автоматический запуск за эту же дату тоже пропустит дубликат.

```powershell
.\.venv\Scripts\python -m app.telegram --user-id 123456789 --send-morning-now
```

Дополнительные материалы команды собраны в папке `docs/`.

- Модели данных в `app/contracts.py`, интерфейсы модели, доставки и решений в `app/ports.py`.
- Для Telegram импортируйте `ApprovalPort`, `ApprovalCardView`, `ApprovalRequest`, `TelegramActor`, `Decision` и `DecisionStatus`. Для автономных тестов подставляйте `FakeApprovals`. При сборке адаптера используйте `ApprovalService(store)` как `ApprovalPort` или `app.state.approvals` из запущенного FastAPI. Передавайте фактический Telegram ID из callback. Для карточки письма берите действие и адресата из `document.mail_dispatch` той же версии. Если поля ещё нет, карточка сообщает, что адресат требует уточнения. При подключении реальной доставки target_ref должен указывать на неизменяемую привязку адресата, зафиксированную для этой версии. Действующий пользователь приходит отдельно из Telegram callback.
- Для почты `Store.receive_mail(channel_id, receipt)` возвращает ID события, профиль и признак повторного входа. Профиль определяется привязкой канала. Получение сохранённого письма и версии требует `profile_id`.
- `FakeModel`, `FakeTransport` и `FakeApprovals` из `app.testing` позволяют выбрать ответ или сбой и проверить записи вызовов. Фикстуры форматов — [CONTRACT_EXAMPLES.json](docs/CONTRACT_EXAMPLES.json).



## Сохранение решений и очередь

Для общего процесса используйте `TelegramChannel` из `app.telegram.channel` с тем же `ApprovalService`, который вызывает workflow. Передайте доверенные функции `chat_for`, `profiles_for` и `build_plan` и путь к постоянной SQLite для контекста исходящих карточек. Общий диспетчер передаёт Telegram-эффекты `approval_notice` и `delivery_update` в `channel.execute`, а обработчик сохранённых событий вызывает `channel.handle_update`. Почтовые, календарные эффекты и поручения передавайте соответствующим транспортам. При подключении реальных данных команда также задаёт обработчик сессий правок и расписание в общем цикле.

- Доверенный обработчик передаёт записанный источник и черновик в `ApprovalService.propose(profile_id, source_id, candidate, ...)`. Метод атомарно сохраняет запрос и служебную карточку Telegram. Повтор открытия не ставит ещё одну карточку. Карточка не содержит разрешения на отправку предлагаемого действия.
- Транспорт уведомлений берёт `approval_notice` из очереди, получает карточку методом `get_pending(profile_id, effect.target_ref, actor)` и отправляет её только когда карточка ещё доступна для записанного Telegram ID. При `None` внешней отправки нет. Непрозрачный ID согласования задаёт основа.
- `decide` сохраняет решение, автора, версию, комментарий и время. `get_decision` возвращает уполномоченному актёру записанное решение в своём профиле. Действие планируется только после `approve`. Его данные формируются из версии, а не из callback. Редактирование создаёт новую версию и заменяет карточку. Если действие уже начали доставлять, оформляйте отдельную коррекцию. Смена руководителя отзывает доступ старого пользователя. Переиздание незакрытых запросов для нового руководителя остаётся отдельным шагом.
- `EffectQueue.run_once(transport)` обрабатывает одну операцию через переданный транспорт. Истёкшая попытка получает статус `unknown`. Повтор после явного временного сбоя ограничен четырьмя попытками. `python -m app retry-effect <id>` возвращает безопасно повторяемую операцию в очередь. Для неизвестного исхода сначала подтвердите у провайдера, что доставки не было, затем укажите `--verified-no-delivery-by <operator-ref>`. Эта отметка сохраняется локально. Команда не вызывает провайдера.
- Для подключения Yandex AI Studio задайте `YANDEX_LLM_API_KEY` и `YANDEX_FOLDER_ID`. `YANDEX_LLM_MODEL` по умолчанию равна `yandexgpt-5.1`. Адаптер создаётся в `app.state.model` и проверяется с подставным HTTP-транспортом. Настройка не требует внешнего вызова при запуске.

SQLite автоматически обновляется с первой схемы с сохранением данных. Сетевой HTTP-API сейчас отдаёт `/health`. Подключение реальных транспортов, фонового обработчика входящих событий, календарных эффектов и HTTP-сессий аватара идёт в следующих интеграционных изменениях.
